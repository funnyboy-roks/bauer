# Contributing

Welcome!  If you're looking into contributing to Bauer, please review
these guidelines (or at least skim them!)

## Feature Requests

If you find that a feature is missing in Bauer, please [open an issue].
In order reduce duplicate issues, please first check for similar open
issues.

## Bug Reporting

If you find a bug or regression in Bauer, please [open an issue].
Providing a minimal example needed to reproduce the bug is very helpful
for determining the issue and what the fix is.

[open an issue]: https://github.com/funnyboy-roks/bauer/issues/new/choose

## Pull Requests

If you wish to contribute code (or documentation) changes, please [open a
pull request] on GitHub.

[open a pull request]: https://github.com/funnyboy-roks/bauer/compare

### Testing

It is important to ensure that all of our code works correctly and that
all generated code compiles and runs as expected.

Most tests can be run using the following command and should work on any
rust version >= the MSRV.

```sh
cargo test
```

The `ui` tests will not be run unless you're using the MSRV (just to
slightly enhance DE).  The `ui` tests should be run using the following
command:

```sh
cargo +1.85 test --test ui
```

#### New Functionality

All new functionality should have at least an integration test in the
`bauer` crate.  The general shape of the integration tests is as
follows:

A single declarative macro is defined (called `tests`) that accepts a
couple of arguments, and is called for each builder kind (currently
`"owned"`, `"borrowed"`, and `"type-state"`).  All test code should be
placed within this macro so that all builder kinds are tested
identically.  Look at `bauer/tests/simple.rs` for an example (and
probably just copy-paste that when writing new tests).

Additionally, changes or additions to attributes should also get a UI
test.  UI testing is done using the
[`trybuild`](https://docs.rs/trybuid) crate.  To create a UI test, add a
file into `bauer/tests/ui` with a name following this pattern:
`{name}.fail.rs` where `{name}` is replaced with a dash-separated short
title for the test.

The test should contain minimal code to produce the error message or
expected output.  Once the test has been written, ensure it has the
correct output with

```sh
cargo +1.85 test --test ui
```

and if the output is correct, save it with

```sh
TRYBUILD=overwrite cargo +1.85 test --test ui
```

### Documentation

Because proc macros lack any method of self-documentation, all changes
should be reflected in the description on the `bauer` crate and the
re-export of `Builder` in `bauer/src/lib.rs`

If documentation changes, the README will also need to be updated.  This
can be done using the `gen-readme.sh` in the repo root.  This script
requires [`cargo-rdme`](https://github.com/orium/cargo-rdme) and
[`sed`](https://www.gnu.org/software/sed/manual/sed.html).

### Style

All code should be formatted using `rustfmt` and linted using `clippy`.  
If CI is complaining about format or linting, install either using
`rustup component add rustfmt` or `rustup component add clippy` and run
either `cargo fmt` or `cargo clippy`.

## LLM/"AI" Contributions

Contributions must not include content generated by large language
models or any other probabilistic tool, including but not limited to
Copilot or ChatGPT. This policy covers code, documentation, pull
requests, issues, comments, and any other contributions.

For more information on why we have this policy, Servo does a good job
of pointing out the various concerns:
<https://book.servo.org/contributing/getting-started#ai-contributions>
